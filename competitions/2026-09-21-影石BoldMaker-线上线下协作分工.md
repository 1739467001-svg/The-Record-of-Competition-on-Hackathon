# 《开图 Unfold》· 线上线下协作分工 v2

> YIN.G ｜ 2026-09-22 Hack Day 1
> **v2 重大简化**：放弃"录连续视频 + 抽帧"，改为**点位全景照片**。
> 数据量从 100GB 降到几十 MB，AI 调用从 999 次降到 20 次，**不需要抽帧**。

---

## 〇、v1 错在哪（记下来，别再犯）

v1 假设"采集 = 录一条 30 分钟连续视频，再抽帧处理"。这个假设直接导致：

| 问题 | 后果 |
|---|---|
| 8K 连续录制 | 单次 **100GB 级**原始数据 |
| 1fps 抽帧 | **999+ 帧**，抽帧本身就要很久 |
| 每帧过多模态 | **999 次推理**，成本和时间都不可控 |
| 上传 | 传不动 |

**根因：把它当成了一个视频处理工程，而它其实是一个空间采样问题。**

> 📌 **回写决策法的一条**：黑客松里，凡是"数据量随时间线性增长"的输入方式都要警惕。
> 先问一句：**能不能改成离散采样？** 能，数据量通常直接掉两三个量级。

## 一、v2 核心：像街景那样，拍点位

**Google 街景不是连续视频，是离散点位 + 点位之间的链接。** 我们照抄这个模型。

一个度假村不需要 999 帧，它需要 **15–25 个关键点位**：

```
大堂 · 前台 · 主餐厅 · 泳池 · 活动中心 · 会议室
房区走廊 · 各出入口 · 主要路口 · 标志性景观
```

**走到那儿，相机举过头顶，按一下。3 秒一个点。**

### 数据量对比

| | v1 录视频 | **v2 拍点位** |
|---|---|---|
| 采集动作 | 30 分钟连续录制 | 20 个点 × 3 秒 |
| 采集总时长 | 30 分钟 | **约 20 分钟**（含走路） |
| 原始数据 | ~100 GB | **20 张照片** |
| 抽帧 | 999 帧 | **不需要** |
| 上传体积 | 传不动 | **40–200 MB** |
| AI 推理次数 | 999 | **20** |
| 处理耗时 | 小时级 | **分钟级** |

### 白捡的好处：画质反而更好

X4 Air 照片模式 **29MP**，远高于 8K 视频抽出来的单帧。
**数楼层、看门牌、认设施全靠细节** —— 拍照不只是更快，是**结果更准**。

## 二、四步流程

```
① 拍   走到关键点位，相机举过头顶，拍一张全景照片（3 秒）
          ↓
② 传   导出 equirectangular JPG → 直接上传（几十 MB）
          ↓
③ 认   AI 读每一张：这是什么地方？有哪些设施？能看到哪些出口与方向？
          ↓  输出：点位语义卡（名称 / 类型 / 设施 / 可见出口）
④ 连   跨点位视觉匹配：两张全景里有共同可见的物体 → 判定相邻
          ↓  输出：场地连接图（谁通向谁）
        = 一张能走的场地图
```

### 第 ④ 步是技术含量的落点

砍掉视频流之后，「技术实现难度 10 分」会掉，用这一步补回来：

- **不做**完整三维重建（SfM/MVS）—— 24 小时做不完
- **只做**跨全景特征匹配（ORB / SIFT 级别）+ 多模态语义辅助，判定点位可达关系
- 效果：**AI 自己把散落的点连成了一张能走的图**

便宜、做得完、有巧思，且路演上一句话讲得清。

## 三、采集规范 v2（线下执行）

> ⚠️ **用照片模式，不要录视频。**

### 相机设置

| 项 | 设定 |
|---|---|
| 模式 | **全景照片**（不是视频） |
| 分辨率 | 最高（29MP） |
| 姿势 | **举过头顶，手臂伸直** —— 避免自己占掉下半球 |
| 站姿 | 按下后**站住别动 2 秒**，等它拍完 |
| GPS 遥控器 | 有就开（能自动带位置更好，没有也不阻塞） |

### 点位怎么选（15–25 个）

| 类别 | 必拍 |
|---|---|
| **出入口** | 每个主要出入口各一张 ← 路径规划的端点 |
| **功能空间** | 大堂、前台、餐厅、泳池、活动中心、会议室 |
| **路口** | 每个岔路口一张 ← **连接关系全靠这些点** |
| **长走廊** | 每 20–30 米一张 |
| **地标** | 场地内标志性景观 |

### 三条铁律

1. **按行走顺序拍，编号连续。** `p01, p02, p03...` —— **顺序本身就是连接信息**，别打乱。
2. **相邻两点要有"共同可见物"。** 站在 p05 能看见 p06 附近的东西 —— 这是第 ④ 步自动连图的依据。
   → 实操：**两点之间不要超过 20–30 米**，拐弯处多拍一张。
3. **拍完当场记一句话。** 用手机备忘录记 `p07 = 泳池边`。三十张之后你会忘，而这一句能省掉线上一大堆猜测。

### 避开

- 正午强逆光（立面全黑）
- 大面积玻璃幕墙正反射
- 有人正对镜头（隐私，且干扰识别）

## 四、交接接口

### 给我什么

| 项 | 规格 |
|---|---|
| **点位照片** | equirectangular JPG，**4096×2048**（首选）或 8192×4096 |
| 命名 | `p01.jpg` `p02.jpg`…**严格按行走顺序**编号 |
| **点位备注** | 一个 txt/表格：`p01=南门入口` `p02=大堂` … |
| 打包 | 一个 zip，**控制在 200MB 以内** |
| 可选 | GPS 轨迹、一段 30 秒全景视频（只用于最终演示片） |

### 导出方式

**Insta360 Studio**：打开 `.insp` → 导出 → 选 **全景（equirectangular）JPG** → 设 4096×2048 → 批量导出。

**如果已经录了视频**（不用全抽，只抽关键时刻的单帧）：

```bash
# 抽某个时间点的一帧（比如第 1 分 23 秒）
ffmpeg -ss 00:01:23 -i 全景.mp4 -frames:v 1 -vf scale=4096:2048 -q:v 2 p01.jpg
```

> 但**更推荐重拍照片** —— 29MP 照片的细节远好于 8K 视频抽帧，而且重拍只要 20 分钟。

## 七、X4 Air 情报（2026-09-22 联网核实，留档）

| 项 | 数值 |
|---|---|
| 视频 | 8K30 / 6K50 / 4K50 ｜ **照片 29MP** |
| 传感器 | 双 1/1.8"，f/1.95 |
| 重量 | 165g |
| 续航 | 8K30 实测约 82 分钟不过热 |
| 防水 | 15m ｜ 连接：BLE 5.2 + Wi-Fi |
| **GPS** | ❌ **机身不带**，需 GPS 遥控器配件 |
| SDK 支持 | ✅ 在 Mobile SDK 列表内（X5 / X4 Air / X4 / X3 / ONE RS / ONE X2 / ONE R / ONE X） |

**SDK 构成**：Camera SDK（连接/状态/预览流/参数/拍摄控制/文件列表/直播）+ Media SDK（预览/**拼接**/导出）。
平台：Android / iOS（X 系列）/ Desktop（X 系列）/ OSC 协议。需 appId + secretKey。

**不依赖 SDK 的备选路**：`.insv/.insp` → Insta360 Studio 导出 equirectangular → 通用格式，谁都能处理。
另：ExifTool 支持解析 `.insv` 元数据；开源 `Insta360GyroExport` 可导出陀螺仪 CSV。
