| 项 | 数值 | 对我们的意义 |
|---|---|---|
| 视频规格 | 8K30 / 6K50 / 4K50 | 采集用 **5.7K–8K 30fps**，够抽帧 |
| 照片 | 29MP | 静态点位补拍可用 |
| 传感器 | 双 1/1.8"，f/1.95 | 单帧像素面积比 X4 大 134% |

| **续航** | **8K30 实测约 82 分钟不过热** | **一块电池能走 2.5 圈**，支撑"30 分钟一圈"的说法 |
| 防水 | 15m | 雨天可采 |
| 连接 | BLE 5.2 + Wi-Fi | 遥控器走蓝牙 |
| SDK | ✅ 在 Mobile SDK 支持列表内 | X5 / **X4 Air** / X4 / X3 / ONE RS / ONE X2 / ONE R / ONE X |

### 🔴 最关键的一条：**X4 Air 本身不带 GPS**

GPS 要靠配件遥控器：

| 配件 | 能力 | 兼容性 |
|---|---|---|
| **GPS Action Remote** | 蓝牙连接，把 **GPS（速度／海拔／方向）写进视频元数据**；可远程启停与改设置 | ✅ 明确兼容 X4 Air |
| **GPS Preview Remote** | 同上 + **实时画面预览** + 内置麦克风 | ✅ 兼容 X4 Air |

> **→ 今天最高优先级：去申请一个 GPS 遥控器。**
> 这就是提案里写的"最大不确定性"的答案——不是技术能不能，是**配件有没有领到**。
> 没有它：路网生成与空间对齐退回手动锚点，工作量 +50%。

## 二、SDK 的真实情况

### 构成

| SDK | 能力 |
|---|---|
| **Camera SDK** | 相机连接、读状态、取预览流、配置参数、控制拍摄、取文件列表、删除文件、全景直播 |
| **Media SDK** | 预览显示、**拼接（stitching）**、图像／视频导出 |

平台：Android SDK ／ iOS SDK（X 系列）／ **Desktop SDK（X 系列）** ／ OSC 协议。

### 🔴 坑：需要 appId + secretKey，要走官方申请

申请入口 `insta360.com/sdk/apply`。**审批周期未知，30 小时比赛等不起。**

> **→ 今天第二优先级：问现场影石工程师「能否当场开通或提供测试凭据」。**
> 拿到 = 加分（可做 Desktop SDK 一键采集，"SDK 使用深度"那 10 分更实）
> 拿不到 = 不阻塞（走下面的备选路）

### ✅ 备选路：完全不依赖 SDK 授权

```
.insv（双鱼眼 + 陀螺仪元数据的私有容器）
   ↓  Insta360 Studio 批量导出
equirectangular 标准全景（2:1 MP4 / JPG）  ← 这是通用格式，谁都能处理
   ↓  上传给线上
Claude 侧：ffmpeg 抽帧 → OpenCV 球面切片 → 千问多模态 → 场地结构
```

补充：**ExifTool 支持解析 .insv 元数据**；开源项目 `Insta360GyroExport` 可导出陀螺仪 CSV。

> **结论：凭据是加分项，不是阻塞项。今天就能开工。**

## 三、采集规范（线下执行，请严格照做）

> 采集质量直接决定线上能不能出结果。**重采一次要 30 分钟，按规范走一次到位。**

### 拍摄参数

| 项 | 设定 | 原因 |
|---|---|---|
| 分辨率 | **5.7K30**（首选）或 8K30 | 5.7K 文件小一半、传得动；抽帧后够用 |
| 帧率 | 30fps | 抽帧按 1–2 fps 采，30 足够 |
| 稳定 | 开启 FlowState | 走动时画面不晃 |
| **GPS 遥控器** | **开启并确认已连接** | 没有轨迹，后面全靠手动 |
| 电量 | 出发前满电 | 82 分钟续航，一圈 30 分钟很宽裕 |

### 走位规范

1. **相机举过头顶**，手臂伸直向上 —— 避免自己的头占掉画面下半球，也让视角接近建筑观察高度。
2. **慢走，约 1 m/s**（比平时散步再慢一点）。走快了抽出来的帧会糊，糊了 AI 数不清层数。
3. **走闭环**：从起点出发，绕一圈**回到起点**。闭环能用来校正轨迹漂移。
4. **关键点停 3 秒**：每栋建筑的正面、每个出入口、每个路口，**站住数三下再走**。
   → 这几帧是"数层数"和"提取立面"的主力素材，糊了就白采。
5. **起点留锚**：出发前在起点拍一张带明显地标的照片，并记下位置。没有 GPS 时靠它对齐。
6. **避开**：正午强逆光（立面全黑）、大片玻璃幕墙正反射。

### 采集清单（营地）

- [ ] 主路一圈（闭环）—— **必做**
- [ ] 主体建筑正面各停 3 秒
- [ ] 所有出入口
- [ ] 一栋有明显楼层线的建筑，**正面平视 + 仰视各一组** ← 验证层数计数的主力样本
- [ ] 起点锚定照片

## 四、交接接口（最重要的一节）

### 你们导出什么给我

**优先级 1（必给）：抽好的帧**

> ⚠️ 8K 视频文件几个 G，上传不现实。**直接给我抽好的帧，这是最靠谱的。**

| 项 | 规格 |
|---|---|
| 格式 | **JPG，等距柱状投影（equirectangular），2:1** |
| 分辨率 | **4096×2048**（够用且传得动）；关键点位可给 8192×4096 |
| 抽帧密度 | **每 1–2 秒一帧**，30 分钟 → 约 900–1800 帧 |
| 命名 | `frame_0001.jpg` 顺序编号，**别打乱顺序**——顺序就是轨迹 |
| 打包 | 按批次分 zip，**单包控制在 200MB 以内** |

Studio 导出后用 ffmpeg 抽帧（命令我下面给）。

**优先级 2（有就给）：轨迹与元数据**

- GPS 轨迹（GPX / CSV：时间戳 + 经纬度 + 海拔 + 朝向）
- 陀螺仪 CSV（`Insta360GyroExport` 导出）
- 起点锚定照片 + 位置说明

**优先级 3（可选）：一小段原始视频**
挑 30 秒最有代表性的一段全景 MP4 给我，用于验证管线与最终演示。

### 抽帧命令（在你们电脑上跑）

```bash
# Studio 导出 equirectangular MP4 之后，每 1 秒抽一帧，缩到 4096 宽
ffmpeg -i 全景.mp4 -vf "fps=1,scale=4096:2048" -q:v 3 frame_%04d.jpg

# 每 2 秒一帧（素材长的时候用）
ffmpeg -i 全景.mp4 -vf "fps=0.5,scale=4096:2048" -q:v 3 frame_%04d.jpg

# 顺带抽元数据看看有没有 GPS
ffprobe -v quiet -print_format json -show_format -show_streams 全景.mp4 > meta.json
```
